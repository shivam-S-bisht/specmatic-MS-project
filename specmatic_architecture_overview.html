9 Implemented Specmatic Features

📜
1. OpenAPI (REST) Contract Testing
📌 What We Implemented
Authored OpenAPI 3.0 specs (order-api.yaml, inventory-api.yaml, payment-api.yaml, shipping-api.yaml) defining exact request/response schemas.
💡 Why We Used It
Guarantees our Express REST routes comply 100% with API contracts. Specmatic generates test inputs dynamically and validates real response schemas against spec definitions.
specmatic test /usr/src/app/order-service
⚡
2. AsyncAPI (Kafka) Event Testing
📌 What We Implemented
Authored AsyncAPI 3.0 spec events-api.yaml defining Kafka channel order-events and payload OrderCreated.
💡 Why We Used It
Validates asynchronous messaging between Order (Publisher) and Shipping/Notification (Subscribers) without manual Kafka payload parsing.
protocol: kafka | host: kafka:9092
🧩
3. Upstream Dependency Mocking
📌 What We Implemented
Configured dependencies.services in specmatic.yaml. Specmatic auto-launches mocks for Inventory (:9001) and Payment (:9002) when testing Order service.
💡 Why We Used It
Enables true isolated testing. The Order service can be verified without starting live downstream payment or inventory databases.
runOptions: openapi (type: mock)
🛡️
4. Resiliency & Mutation Testing
📌 What We Implemented
Enabled schemaResiliencyTests: all in specmatic.yaml across microservices.
💡 Why We Used It
Ensures services handle invalid data robustly. Specmatic automatically mutates payloads (nulls, missing required fields, type mismatches) and verifies the SUT responds with proper 4xx codes instead of 500 crashes.
settings: { schemaResiliencyTests: all }
🔀
5. Polymorphic Discriminators
📌 What We Implemented
Used oneOf and discriminator in payment-api.yaml for payment types (CREDIT_CARD vs BANK_TRANSFER).
💡 Why We Used It
Validates complex real-world data models. Specmatic generates test payloads for every polymorphic branch and validates correct schema selection.
discriminator: { propertyName: paymentMethod }
🔒
6. API Security & Access Control
📌 What We Implemented
Added header authentication (X-API-Key) to protected endpoints like DELETE /orders/{id} in order-api.yaml.
💡 Why We Used It
Verifies security enforcement as part of contract tests. Confirms that missing or invalid API keys return 401 Unauthorized.
parameters: [ name: X-API-Key, in: header ]
📖
7. Dictionary-Driven Generation
📌 What We Implemented
Created contracts/dictionary.yaml defining domain-specific realistic values for item IDs, prices, stock levels, and product names.
💡 Why We Used It
Prevents test failures caused by completely random data. Ensures Specmatic uses valid domain-specific test values during contract test generation and stubbing.
dictionary: { path: ../contracts/dictionary.yaml }
🔄
8. Arazzo Workflow Integration
📌 What We Implemented
Authored place-order.arazzo.yaml executing a multi-step sequence: placeOrder ➡️ getOrder ➡️ cancelOrder.
💡 Why We Used It
Tests complete end-to-end business transactions across services, passing outputs dynamically between steps and generating HTML coverage reports.
specmatic test place-order.arazzo.yaml
🎨
9. Specmatic Studio Workspace
📌 What We Implemented
Configured Docker Studio profile on port 9000 with interactive web navigation and workflow canvas authoring.
💡 Why We Used It
Gives developers and QA engineers a visual UI to inspect contracts, trigger tests against live services, and drag-and-drop endpoints onto an Arazzo canvas.
http://localhost:9000/_specmatic/studio

How Lab Features Improve Testing

🧬
Schema Resiliency Testing
What it does: Automatically mutates valid request payloads (injecting nulls, dropping required fields, sending out-of-bound numbers or corrupt types).
How it improves testing: Replaces hundreds of manual negative test scripts. Eliminates 500 Internal Server Error runtime crashes by verifying upfront that microservices return clean 400 Bad Request validation errors.
📐
Polymorphic Discriminator Validation
What it does: Validates request/response bodies that take multiple distinct structural forms based on a discriminator property (e.g. paymentMethod).
How it improves testing: Prevents silent payload parsing bugs in complex payment workflows by guaranteeing 100% test coverage across every single sub-schema branch (Credit Card vs Bank Transfer).
🔄
Arazzo Integration Workflows
What it does: Executes multi-step business transactions (placeOrder ➡️ getOrder ➡️ cancelOrder), dynamically extracting parameters between steps.
How it improves testing: Moves beyond isolated single-endpoint testing. Catches dynamic state management, parameter extraction, and end-to-end user transaction bugs before production deployments.
🔒
API Security Scheme Testing
What it does: Asserts security constraints (e.g., requiring X-API-Key on destructive operations like DELETE /orders/{id}).
How it improves testing: Automates security compliance testing. Ensures unauthorized or key-less requests are rejected (401 Unauthorized), preventing accidental data loss or security breaches.
📖
Dictionary-Driven Stubbing
What it does: Supplies domain-specific realistic values (valid item IDs, prices, stock levels) to Specmatic's data generator.
How it improves testing: Prevents false-negative test failures caused by arbitrary random numbers. Ensures tests and mock stubs behave realistically like production databases.
🖥️
Specmatic Studio Workspace
What it does: Provides a visual web UI to explore OpenAPI/AsyncAPI contracts, trigger tests interactively, and drag-and-drop endpoints onto an Arazzo canvas.
How it improves testing: Lowers the barrier to entry. Empowers developers, QA engineers, and product managers to visually author, debug, and review integration workflows without writing manual YAML.
